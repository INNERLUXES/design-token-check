# Method

The tool answers one question: do the design tokens of this app respect the accessibility and platform rules before they are handed to developers? It reads the tokens file as data, reads a rules file that says what to compare, computes the contrast ratio of every listed pair and the size of every listed touch target, checks the tokens file for problems of its own, and turns each difference into a finding with a severity, a token path, a file and a line. It never runs a design tool, and it never fetches anything.

Everything it knows about thresholds comes from the official pages that are saved under [research/sources](../research/sources) and listed in [rules-and-sources.md](rules-and-sources.md). A test compares the numbers in `src/data.js` with those saved pages, so the tool and its sources cannot drift apart without a failing test.

## How the files are read

**The tokens file.** A small, strict JSON reader keeps the line of every value. A key given twice in one object is kept, so that the check can report it as `duplicate-name` with both lines. Nesting deeper than 64 levels and more than 200,000 values are refused. An object with a `$value` or a `$ref` is a token, any other object is a group, and the path of a token is the names of its groups and its own name joined with periods. `$root` is a token name and part of the path. [tokens-format.md](tokens-format.md) says which parts of the Design Tokens format are read.

**The rules file.** Plain JSON, read by the same reader (a key twice in one object is refused here). It lists pairs and targets and is described in [rules-file.md](rules-file.md). A rule that is not in the documented format is reported and left out, and the other rules are still checked.

**Paths.** The tokens file is the argument, or `tokens.json` in the folder given as the argument. The rules file is `--rules`, or `token-rules.json` next to the tokens file. Paths are opened with `path.resolve` and shown relative to the folder the command runs in, with forward slashes. Token paths are compared exactly, letter case included, on every system.

## The checks

**Contrast (`low-contrast`).** For every pair and every theme the tool resolves the two tokens to colors, takes the relative luminance of each (WCAG 2.2, with the channels read as 8-bit values) and computes `(L1 + 0.05) / (L2 + 0.05)`, L1 the lighter. The ratio is compared with the threshold as it is, never rounded first, because WCAG says so (4.499 does not meet 4.5). It is shown with two decimals; when the shown value reaches the threshold and the real one does not, the message gives the exact value. The threshold is 4.5:1 for text, 3:1 for large text, and 3:1 for a pair with `"kind": "ui"` (an icon, a border, a focus ring: success criterion 1.4.11). Text is large when it is at least 18 pt, or at least 14 pt and bold. A pair without a size is checked as small text, the stricter rule. A foreground color with alpha below 1 is drawn over the background first, and the message says so; a background with alpha below 1 is `translucent-background`, an error, because the result would depend on what lies behind it.

**Text size.** `pt`, `dp` and `sp` are points as the platforms write them; the Android page uses the same 18 and 14 for `sp`. A `px` or `rem` size is a CSS pixel on the web (WCAG gives 1 pt as 1.333 px, so a pixel is 0.75 pt: 24 px is 18 pt), and a point on `ios` and `android`, where the Design Tokens format makes `px` the equivalent of `pt` and `dp`. A pair names its `platform` to say which; without one a pixel is a CSS pixel, the stricter reading. A `rem` is multiplied by the rem base first. Bold means a weight of 700 or more, the weight the Design Tokens format calls bold.

**Touch targets (`small-target`, `unit-mismatch`).** The token of a target is read as a dimension and converted to the native unit of its platform: `pt` on `ios`, `dp` on `android`, CSS `px` on `web`. Native units are used as they are. A `px` on `ios` or `android` is read as `pt` or `dp`, and a `rem` is multiplied by the rem base; both conversions are shown in the report. A unit that does not belong on the platform (`dp` on iOS, `pt` on Android, `pt` or `dp` on the web, `sp` anywhere) is `unit-mismatch`, an error: the tool never converts it silently, because 1 pt is not 1 CSS pixel. Then the size is compared with the minimum: 44 pt on iOS and iPadOS and 48 dp on Android are warnings, 24 CSS px on the web is an error. For iOS the message also says when the size is under 28 pt, the minimum control size of Apple's page.

**Aliases (`unresolved-alias`, `alias-cycle`, `alias-type-mismatch`).** An alias is a `$value` that is exactly `{path}`, or a `$ref` JSON Pointer such as `#/color/red`. It is followed through other aliases until a token holds a value. An alias that names no token, or names a group, is `unresolved-alias`, reported on the alias whose target is missing; aliases further up the chain are not reported again, but a pair that uses them is `unchecked-rule`. Aliases that lead back to themselves are `alias-cycle`, reported for every token in the cycle with the chain, as the format asks ("an error affecting all tokens in the circular chain"); a token that only leads into a cycle is not part of it. A token with its own `$type` that differs from the type of the token it names is `alias-type-mismatch`.

**Types (`missing-type`, `unknown-type`).** The type of a token is its own `$type`, else the type of the token it is an alias of, else the `$type` of the closest group (the root object counts). A token with none is `missing-type`: the format calls it invalid and says tools must not guess a type from the value. A `$type` that is not one of the format's is a warning.

**Values (`invalid-color`, `invalid-dimension`).** Every token whose type is `color` or `dimension` must hold a value the tool reads, whether or not a pair uses it. The accepted forms are in [tokens-format.md](tokens-format.md). A color in another color space is refused, not converted: a conversion would change the numbers the ratio rests on.

**Names (`invalid-name`, `duplicate-name`, `case-collision`, `invalid-token`).** The format forbids `{`, `}` and `.` in a name and reserves names that start with `$`. A name written twice in one group loses the later token (the first is kept), so it is an error. Two names that differ only in letter case are a warning. A token that also holds child groups, and a value that is neither a token nor a group, are `invalid-token`.

**Rules (`missing-token`, `wrong-token-type`, `unchecked-rule`, `theme-missing`).** A pair or a target that names a token the file does not have is `missing-token`; when a token with the same letters in a different case exists the message names it. A pair that names a token that is not a color, or a target that names one that is not a dimension, is `wrong-token-type`. A rule whose token exists but has no usable value is `unchecked-rule`, so nothing is skipped without a finding. A theme that some pairs list and another pair lacks is `theme-missing`, a warning on the pair that lacks it: the dark theme pair was most likely forgotten, and its colors are not checked.

## Severity

Errors are things the sources call a failure or that make a check impossible: contrast below the WCAG ratio, a web target below 24 px, a token file the format calls invalid. Warnings are guidance that the platform vendors give and that WCAG does not require (44 pt on iOS, 48 dp on Android), and things that may be a slip (a missing theme, a name that differs by case). By default only errors fail the run; `--fail-on warning` fails on both.

## Output

The report keeps every pair and every target, not only the failures, so the numbers behind a pass can be read. Findings are sorted by severity, then by check, file, line and subject, so the same files give the same report on every system. Text that comes from the input goes through `safeText` before it reaches a report.
